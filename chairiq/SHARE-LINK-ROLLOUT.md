# ChairIQ patient access and share-link correction — local candidate

Prepared September 8, 2026 against commit `25154ba` on `vercel-migration`.
**Not deployed. No live database records, schema, settings, DNS, SMS, or email were changed.** Live checks were read-only metadata queries. Tests contain synthetic patient content only.

## Result

The local candidate replaces broad public patient-data access with owner-scoped staff access and exact-token patient reads. New sharing actions issue a new 24-hour link. The database rechecks expiry when fetching the plan; knowing its ID does not grant access. Existing 12-character legacy links deliberately remain non-expiring for compatibility.

The live service still runs the old code and permissions until a separately approved rollout. These local results do not establish live confidentiality or expiry enforcement.

## Changes

1. `supabase/migrations/20260908052729_secure_plan_share_links.sql` creates the missing share-link table or hardens its old version, with owner-scoped link reads/inserts, a database-assigned 24-hour expiry, exact-token validation and view counting. It expires any preexisting share-table tokens because old policies exposed them or allowed forgery. It does not invalidate legacy plan tokens.
2. `supabase/migrations/20260908142423_scope_patient_data_access.sql` removes existing permissive policies on patients, plans, procedures, patient analytics, SMS/logs/views/reminders. Staff access requires matching ownership. New patient/plan records default to the signed-in account; clients cannot reassign ownership or attach a foreign patient. Nullable audit references remain supported but non-null references must match their plan.
3. The `get_patient_plan` RPC returns one exact token's patient name/language, plan details, procedures and patient-image metadata. It omits phone numbers, ownership and other bearer tokens. Its privileged implementation is in `chairiq_private` with a fixed search path and narrow grants. Patient fetches use this RPC, including legacy links; an expired or failed share lookup cannot fall back to public-by-ID reads.
4. Previously exposed patient metrics functions become invoker functions with authenticated execution only, so their reads follow owner policies. The old session-update trigger function also becomes invoker to prevent cross-owner writes.
5. Patient images use the private `patient-images` bucket and a new `patient_plan_images` table with a real procedure foreign key. Generic educational images keep their existing public bucket and canonical-procedure foreign key. The migration aborts if old patient-specific public objects or metadata exist, requiring a separately reviewed Storage API move. The inspected live project had zero of both.
6. Patient image downloads use the new `supabase/functions/patient-plan-image` Edge endpoint. Every POST revalidates the exact link through `get_patient_plan`, checks that the requested image occurs in that procedure’s metadata, downloads with server-only credentials and returns binary bytes with private/no-store headers. Direct anonymous Storage access is denied. The client explicitly reads `response.blob()` using only the public anon key, without staff cookies or sessions. The private bucket restricts file types and size. Downloaded content already seen by a recipient cannot be withdrawn by expiry.
7. Copy/send/retry/resend controls require expiring links. Sharing actions issue fresh tokens so a near-expiry link is not resent. A link-creation failure leaves the saved plan intact, shows an error and offers a link-only retry. Staff resend obtains contact details through owner-scoped table reads; it does not expose them through the patient RPC.
8. `supabase/reviewed-operations/assign-confirmed-plan-owners.sql` records the user's explicit confirmation that both existing plans belong to their verified ChairIQ dentist account. It targets exactly the two inspected plans and their one patient, checks that the account exists and ownership is still null, and aborts if relationships or related plans changed. It uses a transaction and table locks. It is **not executed and not an automatic migration**.

## Verification and limits

The automated suite runs actual SQL in in-memory PGlite PostgreSQL, using synthetic records, roles, grants, row policies, functions, triggers and constraints. It covers missing/old share tables, exposed-token invalidation, expiry, enumeration, owner isolation, foreign patient references, nullable logs, metrics access, private image policy decisions and the guarded ownership operation. Service tests replace only remote service boundaries and cover token fetching, expiry between requests, private upload/download behavior and fresh resend issuance. No test can send a real SMS/email.

The fixture includes the live canonical-procedure foreign key that previously prevented patient-image metadata inserts. It is still a reduced schema, not a clone of production. The candidate has now also been tested on a disposable full Supabase branch, including real Auth, PostgREST, Edge Functions, Storage and browser CORS. The initial custom-header Storage design failed a real CDN caching test and was replaced; it must not be restored.

The production build and complete test suite must pass on the final patch. See the dated verification record below. A clean dependency installation passed in the previous local phase; dependency resolutions remain unchanged except for pinned development-only `@electric-sql/pglite@0.3.14`.

## Before a live rollout

1. The disposable full Supabase test is complete; see the verification record below. The separately discovered `sms_consent` exposure now has a standalone reviewed permission fix in `20260908182644_protect_sms_consent.sql`. Read-only inspection found zero rows, no policies or column grants, no public database function/view/trigger consumers, and no callers in the repository or the deployed send-sms Edge Function. The consent page is informational. The migration enables RLS, revokes all ordinary-client table privileges and adds a restrictive deny policy; existing service-role access and records are preserved. Thirteen synthetic SQL tests passed, including accidental future permissive policies. Independent review found no issue. This migration was tested locally, not on the deleted Supabase branch, and still needs explicit approval before live application. Uninspected external integrations cannot be ruled out. Do not expose `chairiq_private` through the Data API.
2. Verify the exact ownership mapping again immediately before execution. User confirmation authorizes preparation, not applying the live change. Unowned rows not included in the mapping stay inaccessible to staff. Do not infer other ownership from names or profiles.
3. Decide whether retaining non-expiring legacy links is acceptable. Because plan tokens were previously readable through broad public policies, existing tokens should be treated as potentially exposed. Revoke/rotate them only with an explicit compatibility and patient-communication decision.
4. Reconcile migration history. The live migration listing was empty; this does not prove SQL was never applied manually. **Never run the entire repository migration directory against live.** It contains `20251230041359_reset_patient_data.sql`, which deletes patient/plan data, and old mock-data seed scripts. The first correction does not require the insecure March share-link migration to be applied first.
5. After full testing, review a coordinated rollout of the two new SQL migrations, exact ownership operation, matching app and new `patient-plan-image` Edge Function with JWT verification enabled. Obtain a verified recovery point and explicit approval before live changes. The data-access migration makes the old anonymous table-reading client incompatible, so it cannot be treated as an independent deployment. No DNS, Twilio or production configuration change is included in this candidate.
6. Do not rerun the corrective SQL manually as an idempotent reset: the first migration intentionally expires preexisting share-table tokens. Restoring the old public data policies is not an acceptable rollback. Use the tested recovery/forward-fix plan.

The Storage design follows Supabase's [private download documentation](https://supabase.com/docs/guides/storage/serving/downloads) and [operation-specific RLS guidance](https://supabase.com/docs/guides/storage/security/access-control); these documents do not substitute for testing the configured project.
